# fsの実装

xv6のファイルシステムは、
virtio | buf | log | inode+file
という階層を組む

## VirtIO
qemuが実装しているブロックデバイスの仮想化機構

PLICとして割り当てられたアドレスに色々な書き込み領域が存在していて、そこにいくつかの配列のアドレスを保存しておく。

ディスクへの読み書きは、別で割り当てた領域のアドレスを、先程アドレスを保存した配列上に所定のフォーマットで格納して行う

### virtio_disk_rw
buf構造体を与えられると、その中身をディスクに書き込む・読み込む
読み書きはブロック単位でのみ可能

## Buffer
ディスクから毎回読み書きすると遅いので、ディスクとの読み書きはBufに対して行い、一連の操作が終わった段階でまとめて書き込む

Bufは1ブロック分のu8を持つ。
BCacheにNBUF個のBuf構造体が保存されていて、連結リストとして管理されている

Bufの取得は、まず欲しいディスク領域のBufがCache上に存在しているかを確認し、なければLRUで最も古いフリーなBuf構造体を割り当てる。

breadを呼び出すと、ディスクの情報を読み込んだbufを返してもらえる。

その後、Bufから必要な読み書きを行う。

最後、bwriteを実行するとbufの中身がディスクに書き戻される

## Log
書き込みを普通に行うと、ある原始的に行わないといけない操作について状態が破損する可能性がある。

そのため、まずFSのLog領域に書き込み、書き込み完了の印をつけた上で、その内容を正しい位置に転送する。こうすることで、書き込み完了したのに正しい位置にないブロックが存在したとき、Log領域から復元することができ、復元が可能となる

commitでコミットを行うが、
write_log：ブロックのキャッシュに書かれている内容をログブロックに書き込む
write_head：ログヘッダ領域にログヘッダ（ログブロックのアドレス一覧）を書き込む
install_trans：ログをブロックに移す

### LogHandle
ログハンドルがログへの書き込みを司る。主にシステムコールの書き込みがログへの書き込み限界を超えないように管理する。
LogHandle::newを行う際、実行中＋書き込み待ちのシステムコールが多すぎるとsleepする

dropするとき、もし実行中のシステムコール数が0なら、コミットを行う

## inode
ディスク上の領域はブロックごとに区切られている。
inodeは、一連のブロックを1まとまりにして管理する構造体である。
ディレクトリ中のディレクトリエントリがinode numberとパスを関連付ける

DInodeがディスク上に保存されているInode構造体で、Inodeがメモリ上に移されたinode構造体

まず、メモリ上にinode構造体を確保する（配列上の空きindexを取ってくる）。
次に、構造体をロックする際にディスクから中身を取ってくる。

guard.readをすると、与えられたアドレス範囲に中身を書き出す
guard.writeをすると、ブロックのBufに中身を書き出し、inode構造体も書き戻す（書き込み時にファイルサイズが増え、ブロックアドレスリストが更新された可能性があるため）

ファイルサイズが小さすぎる場合は、新しいブロックを確保してそこに書き込む。ballocがbitmapの中から未使用のブロックを検索し、それをinodeのaddrsに登録する。

inode構造体のアンロックやドロップのときには、特別なことはしない（writeですでにブロックへの下記戻しをしているため）が、inodeへの参照が0となった場合にはinode構造体も消す

## File
Inode, Device, Pipeなどを包含する。
readやwriteといった書き込みに対して、適切なドライバを呼び出す

Inodeへの書き込みでは、1度の書き込みで可能な最大長が決まっているため、
所定のサイズごとに区切ってinode.writeを呼び出す

## fs
ファイルシステムは以上の機構を全て合わせたものの呼称である。
fs.rsでは、ディレクトリ操作関連（linkや、パスからinodeを検索する処理など）を実装している。

### SuperBlock
inode blockの数や、bitmapの数、開始アドレスを保存している
